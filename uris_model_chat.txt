● Let me go through each stage honestly — including where I think the design is
  sound and where it could backfire.

  ---
  Stage 1 — Early: DepthEncoder + DepthFusionModule

  What it does

  RS depth + validity mask → small 4-scale CNN → feature maps at 1/4…1/32
  resolution → added residually (via 1×1 conv, zero-init) into the left image 
  feature maps from the backbone.

  Why the zero-init matters

  At training start, the 1×1 projections output exactly zero, so the model
  starts from the pretrained stereo behaviour. The network has to earn the depth
   contribution via gradient descent. This is a sound training stability trick.

  The validity masking per scale

  v4  = F.max_pool2d(validity, 2, 2)   # H/4
  d4  = self.stage1(x2) * v4
  Using max-pool on the validity mask means a coarse-scale cell is valid if any
  fine-scale pixel in it was valid. That's intentionally conservative — better
  to use a slightly noisy valid region than to zero out real signal.

  Where it can create noise over signal

  The depth features are added to the left features only. Those left features
  then go into the cost volume — which is a cross-correlation between left and
  right. The right features are untouched. So you're introducing an asymmetry:
  the left side now "knows" something about depth that the right side doesn't.
  If the RS depth is accurate, this helps the left features tell the cost volume
   "look near this disparity". If RS depth is wrong (reflective surface,
  occluded region, edge bleed), it corrupts the feature matching for that region
   and the cost volume gets a misleading signal that's hard to override
  downstream.

  Verdict: This is the riskiest of the three. The benefit is real but the
  corruption of feature-matching asymmetry is a genuine concern. Worth ablating
  — Stage 2 alone may give most of the gain at lower risk.

  ---
  Stage 2 — Mid: Gaussian prior bias on cost volume logits

  What it does

  After the cost volume produces logits over disparity bins (shape B × D × H/4 ×
   W/4), this adds a Gaussian bump centered at the disparity predicted from RS
  depth:

  d_idx      = arange(D)                          # disparity bin index
  prior_bias = -0.5 * ((d_idx - disp_prior_14) / sigma)²
  logits     = logits + depth_prior_scale * prior_bias

  Why this is the most principled stage

  It's a proper Bayesian-style prior injection. The logits are log-probabilities
   (before softmax), so adding a Gaussian in log-space is exactly equivalent to
  multiplying the stereo probability distribution by a Gaussian prior — which is
   the textbook way to combine two uncertain measurements. The stereo evidence
  can still dominate if it's strong; the prior only matters when stereo evidence
   is weak (textureless regions, bad lighting).

  The two learned scalars

  - depth_sigma (init=4.0 disparity units at 1/4 scale): controls how tight the
  prior is. Too small → a slightly wrong RS reading creates a sharp misleading
  spike. Too large → the prior is so diffuse it does nothing.
  - depth_prior_scale (init=0.1): overall weight. Starts near-zero, network
  learns how much to trust RS globally.

  Where it can create noise

  RS depth suffers from mixed-pixel / edge bleed — at depth discontinuities the
  sensor averages foreground and background, giving a reading that belongs to
  neither. In those pixels the Gaussian bump is centered at a phantom disparity,
   and if depth_sigma has learned to be tight, it actively suppresses the
  correct bin. The validity mask doesn't help here — the pixel is valid, just
  wrong.

  Verdict: The cleanest and lowest-risk stage. This one is almost certainly
  worth keeping.

  ---
  Stage 3 — Late: DepthInitBlend (GRU initialisation)

  What it does

  Takes three inputs at 1/4 resolution: the stereo soft-argmax stereo_init, the
  RS-derived disparity disp_prior_14, and the validity mask. A small 3-layer CNN
   predicts a per-pixel blend weight w = sigmoid(...), and outputs:

  blend_w * disp_prior + (1 - blend_w) * stereo_init

  The last conv is bias-init to −5 → sigmoid(−5) ≈ 0.007 at the start, so the
  GRU initialises almost entirely from the stereo soft-argmax.

  The claimed benefit

  The GRU is iterative (8 iterations here). A better initialisation means it
  needs fewer iterations to converge, and reduces the risk of getting stuck at
  the wrong disparity. RS depth, even noisy, can cut across textureless regions
  where stereo's soft-argmax is genuinely confused.

  The redundancy problem

  This is where I'd push back hardest. After Stage 2, stereo_init is already 
  biased toward the RS prior — the Gaussian bump in logits has already nudged
  the soft-argmax in that direction. Stage 3 then takes that already-biased
  estimate and blends it again with the raw RS disparity. In the good case (RS
  correct, Stage 2 worked) you've over-counted the RS signal twice. In the bad
  case (RS wrong at an edge), the GRU starts from the wrong disparity and has to
   spend all 8 iterations fighting its way back to the correct answer — the
  iterative mechanism that's supposed to be robust to bad init is now working
  against you.

  The other risk: local minima

  RAFT-style GRUs are known to be fairly robust to initialisation within a 
  reasonable range. But "reasonable" here means within a few disparity units. If

  Verdict: Most questionable of the three. Partially redundant with Stage 2, and
   introduces GRU convergence risk. If you had to cut one stage, cut this one
  first and see if loss changes at all.

  The double-counting problem

  stereo_init  ≈ α·disp_prior + (1-α)·pure_stereo        # after Stage 2

  The effective weight on the RS prior is higher than either stage intended.
  When RS is correct this is fine; when RS is wrong at an edge, both stages
  compound the error into the GRU starting point.

  parameters competing for gradient signal. With less data, a single well-placed
